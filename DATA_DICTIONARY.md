# Data Dictionary — Compliance Platform (multi-tenant)

> Esta es una base **multi-tenant**: decenas de instituciones financieras (bancos,
> ALYCs, fintechs, EMIs) comparten las mismas tablas. **Toda** consulta debe
> scopearse por `tenant_id`. Cruzar datos entre tenants es incorrecto.
>
> Este diccionario documenta **algunas** tablas y columnas, a propósito **no todas**.
> Hay enums, columnas y estructuras JSONB que vas a tener que descubrir explorando
> la data. Lo que está acá es correcto; lo que falta, es parte del ejercicio.

## Convenciones globales

- `tenant_id BIGINT` está en casi todas las tablas (todas menos `tenants` y los
  catálogos lookup). Es la columna de scoping obligatoria.
- IDs: `BIGINT` autoincremental (`GENERATED BY DEFAULT AS IDENTITY`).
- Sufijo `_at` ⇒ `TIMESTAMPTZ` (UTC). Sufijo `_date` ⇒ `DATE` (sin hora, sin zona).
- `deleted_at TIMESTAMPTZ NULL`: soft-delete. **Las filas borradas siguen en la
  tabla.** Toda respuesta normal las excluye (`deleted_at IS NULL`).
- Enums: `TEXT` con `CHECK (... IN (...))` en MAYÚSCULAS. No son tipos enum
  nativos: vas a tener que mirar los valores reales en la data.
- `metadata JSONB`: presente en varias tablas; guarda información semiestructurada.

## Fecha de corte

La base es un snapshot a **`AS_OF = 2026-06-01`**. No hay datos posteriores a esa
fecha. Cualquier noción de "hoy", "este año" o "último trimestre" se interpreta
relativa a esa fecha.

Los períodos se interpretan en calendario: **"este año"** = año calendario en curso
(1-ene-2026 .. AS_OF) y **"último trimestre"** = trimestre calendario cerrado
(ene–mar 2026). Algunos tenants tienen `fiscal_year_start_month` en su config: es un
atributo real del negocio, pero **no** redefine estos períodos.

## Tablas (selección documentada)

### `tenants`
La raíz. Una fila por institución.

| columna | tipo | nota |
|---|---|---|
| `id` | BIGINT | PK |
| `slug` | TEXT | identificador legible, único (ej. `banco_norte`) |
| `legal_name` | TEXT | |
| `kind` | TEXT | `BANK` / `ALYC` / `FINTECH` / `EMI` |
| `is_active` | BOOLEAN | hay instituciones dadas de baja |
| `created_at` | TIMESTAMPTZ | |

### `tenant_config`
Configuración de negocio **por tenant**, como pares clave/valor versionados en el
tiempo. Una fila por `(tenant_id, key, effective_from_date)`.

| columna | tipo | nota |
|---|---|---|
| `tenant_id` | BIGINT | |
| `key` | TEXT | nombre del parámetro |
| `value` | JSONB | valor (escalar JSON) |
| `effective_from_date` | DATE | desde cuándo aplica |

Algunas `key` que vas a encontrar (puede haber más):

- `high_risk_score_threshold` — umbral de score para "riesgo alto". **Varía por
  tenant.** Puede estar **versionado**: si hay varias filas con la misma `key`,
  la vigente es la de mayor `effective_from_date <= AS_OF`.
- `fiscal_year_start_month` — mes (1–12) en que arranca el año fiscal del tenant.
  No todos arrancan en enero.

> El `value` es JSON escalar: para leerlo como texto, `value #>> '{}'`; como int,
> `(value #>> '{}')::int`; como bool, `(value #>> '{}')::bool`.

### `clients`
Entidades onboardeadas (KYC). Tabla central de identidad.

| columna | tipo | nota |
|---|---|---|
| `tenant_id` | BIGINT | |
| `id` | BIGINT | PK |
| `external_ref` | TEXT | id del cliente en el sistema del tenant |
| `full_name` | TEXT | |
| `document_type` | TEXT | `DNI` / `CUIT` / `PASSPORT` / `CDI` |
| `document_number` | TEXT | **el formateo no está normalizado** (con/sin guiones) |
| `email`, `phone` | TEXT | |
| `birth_date` | DATE | |
| `country` | TEXT | código de país |
| `onboarding_status` | TEXT | `PENDING` / `APPROVED` / `REJECTED` / `MANUAL_REVIEW` |
| `onboarded_at` | TIMESTAMPTZ NULL | a veces null aunque esté aprobado |
| `manual_high_risk_flag` | BOOLEAN | marca manual de riesgo alto |
| `metadata` | JSONB | |
| `created_at`, `updated_at` | TIMESTAMPTZ | |
| `deleted_at` | TIMESTAMPTZ NULL | soft-delete |

> No existe una columna `person_id`. Si dos filas son "la misma persona", eso se
> infiere (mismo documento, mismo email, nombre parecido), no está marcado.

### `risk_assessments`
Score de riesgo del cliente, **historizado**: un cliente puede tener varias filas
a lo largo del tiempo.

| columna | tipo | nota |
|---|---|---|
| `tenant_id` | BIGINT | |
| `id` | BIGINT | PK |
| `client_id` | BIGINT | |
| `score` | INT | 0–100 |
| `model_version` | TEXT | |
| `assessed_at` | TIMESTAMPTZ | |
| `is_current` | BOOLEAN | marca la evaluación vigente del cliente |
| `deleted_at` | TIMESTAMPTZ NULL | |

> Hay **exactamente una** fila `is_current = true` por cliente (no borrada). El
> score actual del cliente es el de esa fila.

### `screenings`
Cada corrida de un cliente contra listas (sanciones, PEPs, etc.).

| columna | tipo | nota |
|---|---|---|
| `tenant_id` | BIGINT | |
| `id` | BIGINT | PK |
| `client_id` | BIGINT | |
| `screened_at` | TIMESTAMPTZ | |
| `result` | TEXT | `NO_HIT` / `POTENTIAL_HIT` / `CONFIRMED_HIT` / `DISCARDED` |
| `metadata` | JSONB | detalle del match (ver abajo) |
| `deleted_at` | TIMESTAMPTZ NULL | |

Forma del `metadata` cuando hay un match PEP confirmado:

```json
{
  "is_pep": true,
  "matches": [
    {"watchlist_code": "PEP_AR", "score": 0.93, "matched_name": "JUAN PEREZ"}
  ]
}
```

> `result = 'DISCARDED'` significa que el analista descartó el hit (≈ falso
> positivo): **no** es un PEP/sanción real. `POTENTIAL_HIT` tampoco está
> confirmado.

### `alerts`
Alertas de monitoreo AML.

| columna | tipo | nota |
|---|---|---|
| `tenant_id` | BIGINT | |
| `id` | BIGINT | PK |
| `client_id` | BIGINT NULL | |
| `rule_code` | TEXT | regla que disparó (ver `alert_rules`) |
| `status` | TEXT | `OPEN` / `IN_REVIEW` / `ESCALATED` / `CLOSED_TRUE_POSITIVE` / `CLOSED_FALSE_POSITIVE` |
| `severity` | TEXT | `LOW` / `MEDIUM` / `HIGH` / `CRITICAL` |
| `triggered_at` | TIMESTAMPTZ | cuándo se disparó |
| `first_reviewed_at` | TIMESTAMPTZ NULL | primera revisión (null = sin revisar) |
| `closed_at` | TIMESTAMPTZ NULL | |
| `case_id` | BIGINT NULL | sin poblar; el vínculo alerta↔caso vive en otra parte del esquema |
| `deleted_at` | TIMESTAMPTZ NULL | |

> `CLOSED_FALSE_POSITIVE` **no** es un hallazgo real. El SLA de revisión vive en
> `tenant_config` (en horas) y varía por tenant.

| columna | tipo | nota |

| `tenant_id` | BIGINT | |

### `transactions`
El grueso del volumen. Movimientos de los clientes.

| columna | tipo | nota |
|---|---|---|
| `tenant_id` | BIGINT | |
| `id` | BIGINT | PK |
| `client_id` | BIGINT | |
| `amount` | NUMERIC(18,2) | **no es float**: usá aritmética exacta |
| `currency` | TEXT | `ARS` / `USD` / `EUR` / `USDT` |
| `direction` | TEXT | `IN` / `OUT` |
| `channel` | TEXT | `WIRE` / `CASH` / `CARD` / `CRYPTO` |
| `tx_date` | DATE | fecha contable (calendario) |
| `booked_at` | TIMESTAMPTZ | timestamp de registro |
| `status` | TEXT | `SETTLED` / `PENDING` / `REVERSED` |
| `deleted_at` | TIMESTAMPTZ NULL | |

> **No hay tabla de tipos de cambio (FX).** Montos en monedas distintas **no se
> suman** entre sí. `REVERSED` no cuenta como movimiento efectivo.

### Catálogos / lookup
`countries`, `document_types`, `channels`, `alert_rules`, `watchlists`. Tablas de
referencia chicas.

> Hay **más tablas** en el esquema además de las listadas acá (de auditoría,
> documentos, contrapartes, etc.). No todas son necesarias para responder las
> preguntas comunes; explorá antes de joinear de más.

## Índices disponibles

La base es grande y tiene `statement_timeout = 15s`. Una consulta que **no** usa
los índices hace full scan y muere por timeout. Los índices existentes son:

| índice | tabla | columnas |
|---|---|---|
| `idx_clients_tenant_onboarded` | `clients` | `(tenant_id, onboarded_at)` |
| `idx_clients_tenant_active` | `clients` | `(tenant_id) WHERE deleted_at IS NULL` |
| `idx_clients_tenant_docnum` | `clients` | `(tenant_id, document_number)` |
| `idx_ra_tenant_client_current` | `risk_assessments` | `(tenant_id, client_id) WHERE is_current` |
| `idx_screenings_metadata_gin` | `screenings` | `GIN (metadata jsonb_path_ops)` |
| `idx_screenings_tenant_client` | `screenings` | `(tenant_id, client_id)` |
| `idx_alerts_tenant_status_triggered` | `alerts` | `(tenant_id, status, triggered_at)` |
| `idx_alerts_tenant_unreviewed` | `alerts` | `(tenant_id, first_reviewed_at) WHERE first_reviewed_at IS NULL` |
| `idx_tx_tenant_date` | `transactions` | `(tenant_id, tx_date)` |
| `idx_tx_tenant_client_date` | `transactions` | `(tenant_id, client_id, tx_date)` |
| `idx_cases_tenant_status_opened` | `cases` | `(tenant_id, status, opened_at)` |
| `idx_tenant_config_lookup` | `tenant_config` | `(tenant_id, key, effective_from_date)` |
